# DA005 — Read-only Red/Blue offline evidence handoff

This cross-team software check links one **pending, non-executed** Red Team
UCB1/random scenario proposal to a separately pinned PCAP -> Zeek import and
to Blue Team's **recomputed offline research predictions on the SAME Zeek
`conn.log` bytes**. It is not an attack, a replay, a verified detection,
a SOC case or a real-time measurement.

## Inputs and boundaries

The operator must already have, outside Git, (1) a Red Team planning timeline
JSON with one pending proposal, (2) a classic PCAP and its original Zeek
`conn.log` plus `offline_import_report.json`, (3) a data-only Zeek
research model exported and independently SHA-256-pinned, and (4) the
`new-predictions.json` generated by `score_zeek_new_log.py` for that exact
log. Independently record **all five** hashes: Red audit, import report,
original Zeek log, Blue model and Blue prediction report. Preserve original
PCAP separately; its hash is rechecked against the pinned import report.
Use the actual authorized private Host-only CIDR, not the example below.

From the repository root, on Windows Python 3.12.9:

```powershell
py -3.12 scripts/verify_red_blue_offline_handoff.py `
  --audit "C:/DA005-private/red-team-audit.json" `
  --expected-audit-sha256 "<AUDIT_SHA256>" `
  --offline-import-report "C:/DA005-private/session/zeek/offline_import_report.json" `
  --expected-offline-import-report-sha256 "<IMPORT_REPORT_SHA256>" `
  --pcap "C:/DA005-private/session/original.pcap" `
  --log "C:/DA005-private/session/zeek/conn.log" `
  --expected-log-sha256 "<ZEEK_LOG_SHA256>" `
  --model "C:/DA005-private/models/zeek-research-model.json" `
  --expected-model-sha256 "<MODEL_SHA256>" `
  --blue-report "C:/DA005-private/session/zeek/new-predictions.json" `
  --expected-blue-report-sha256 "<BLUE_REPORT_SHA256>" `
  --cidr "<APPROVED_HOST_ONLY_CIDR>" `
  --confirm-authorized --confirm-offline-only --confirm-fixture-reviewed
```

The command only prints a bounded JSON summary; it writes no files and
never opens sockets. All inputs must be private regular files outside the
repository, with distinct paths; Blue report must be JSON alongside
`conn.log`. Red history is replayed to check deterministic proposal
selection and disabled execution. The original PCAP/import/log hashes,
PCAP framing and declared CIDR are checked. Blue report is independently
SHA-pinned and **every score is recomputed** from the pinned model and log.
A source-hash/flow-count disagreement or any tampering fails closed.

The output includes proposal/scenario/strategy, hashes, flow count and Blue
**research candidate count** only. It intentionally excludes IPs, Zeek UIDs,
packet contents, labels and individual probabilities. Even a successful join
does **not** verify scenario-to-packet correspondence, authorization, VMware
isolation, capture authenticity, independent attack labels, TEST exclusion,
model authorship, Blue Team operational detection or Red Team execution.
The policy's operator-entered feedback must never be treated as verified
Blue Team outcomes or a measured UCB1-vs-random reward. The PCAP fixture
may be semantically unrelated to the Red scenario despite matching hashes.

## Real-Zeek CI integration acceptance (proposed 31/10/2026)

The separate GitHub workflow `.github/workflows/real-zeek-offline-smoke.yml`
now runs `tests/ci_real_zeek_red_blue_handoff.py` **after** the existing
production importer, Blue research scoring, independent score review and
disposable manual Unclassified SOC-case acceptance. The new stage reuses the
actual Zeek `conn.log` produced by the network-disabled container from a
deterministic **benign synthetic PCAP**, not a hand-authored Zeek fixture.

It creates a **pending, non-executed** Red UCB1/random proposal in the CI
temporary directory and runs the production read-only handoff library and
CLI against the exact existing original PCAP, importer report, Zeek log,
synthetic-label Blue model and prediction JSON. It checks matching hashes,
flow counts, library/CLI agreement, all non-operational flags, missing
operator confirmation, wrong Red audit pin and a changed Blue report whose
SHA-256 is deliberately re-pinned. It also verifies that existing model,
PCAP, log, prediction, import and disposable SQLite case bytes remain
unchanged. The resulting bounded artifact is
`ci_real_zeek_red_blue_handoff_report.json` in
`da005-real-zeek-synthetic-smoke` (7-day retention).

Run the unit-only contract tests on Windows:

```powershell
py -3.12 -m pytest -q tests/test_ci_real_zeek_red_blue_handoff.py
```

**Scientific boundary:** The pending Red proposal is not executed and has
no independently verified relationship to the benign packets. The model
was fitted on arbitrary synthetic labels. All pins are generated within
the same CI job, not independently preregistered. The integration tests
exercise software plumbing with an actual Zeek binary, but do not verify
a student-owned VMware capture, physical Host-only isolation, independent
labels, attack detection, operational alerts or event-to-SOC latency.
Only a separate authorized Windows/VMware experiment can establish those
claims. At authoring, the new PR-head CI is **not yet verified**; check the
specific workflow runs before marking this acceptance complete.
